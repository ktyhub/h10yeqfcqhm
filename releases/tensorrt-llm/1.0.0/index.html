TensorRT-LLM v1.0.0

major PublishedSep 24, 2025 SourceNVIDIA/TensorRT-LLM Chinese translation

TensorRT-LLM v1.0.0

Highlights

  • PyTorch is now the default — TensorRT-LLM 1.0 makes the stable PyTorch architecture the default for both LLM and trtllm-serve, while the LLM API receives compatibility guarantees for subsequent releases. Existing TensorRT workflows may silently follow a different execution path after upgrading; explicitly select the backend where behavior must remain unchanged and revalidate accuracy and performance.

  • Configuration APIs require migration — Rename mixed_sampler to enable_mixed_sampler and LLM.autotuner_enabled to enable_autotuner, and update references to the renamed cuda_graph_config.padding_enabled field. PyTorch KV-cache configuration is consolidated under LLM/executor::KvCacheConfig, replacing batch_manager::KvCacheConfig. Deprecated LoRA arguments, TrtGptModelOptionalParams, and Torch ptuning knobs are removed; the Triton llmapi + TensorRT backend integration is also no longer supported.

  • Serving APIs gain finer control — The OpenAI-compatible endpoint adds JSON Schema support, /v1/completions gains a detokenize option, and request-level performance metrics are exposed through LLMAPI and Triton. Triton also gains request cancellation. Dynamic speculative-decoding toggles and guided decoding with overlap scheduling give operators more control over throughput/latency trade-offs without restarting workers.

  • LoRA becomes more practical under memory pressure — PyTorch LoRA is supported in trtllm-serve, with adapter eviction and CPU-cache reload support (#6786). This enables serving more adapters without retaining every one in GPU memory, but changed default cache sizes and peft_cache_config behavior mean existing deployments should review capacity and eviction expectations.

  • KV-cache reuse expands, with an important caveat — Cache reuse now covers in-flight generation, multimodal models, and two-model engines, alongside PyTorch pipeline-parallel disaggregation and disaggregated n-gram speculation. These features can reduce repeated prefill and improve utilization. However, disaggregated serving combined with pipeline parallelism and KV-cache reuse has a known hang; disable KV-cache reuse until it is fixed.

  • Model coverage expands, but hardware qualification matters — New support includes Mistral 3.1 VLM, Phi-4-multimodal, EXAONE 4.0, Qwen3 dense/MoE, and Gemma3 LoRA. Blackwell gains DeepSeek R1 FP8 and MLA chunked prefill, Hopper gains additional MLA/XQA paths, and PyTorch adds MXFP8×MXFP4 support. Rebuild custom images against the new PyTorch/Triton 25.06 containers and updated ModelOpt 0.33/transformers 4.53.1 dependencies. Critical fixes include MLA illegal memory access (#6437), DeepEP with online EPLB (#6429), and PD + MTP + overlap accuracy (#6136); single-GPU-per-node multinode remains known-broken, and Llama 3.x/4 pipeline parallelism with FP8/NVFP4 requires TRTLLM_LLAMA_EAGER_FUSION_DISABLED=1.

TensorRT LLM Release 1.0

TensorRT LLM 1.0 brings 2 major changes: the PyTorch-based architecture is now stable and the default experience, and the LLM API is now stable. For more details on new developments in 1.0, please see below.

Known Issues

  • When using disaggregated serving with pipeline parallelism and KV cache reuse, a hang can occur. This will be fixed in a future release. In the meantime, disabling KV cache reuse will fix this issue.
  • Running multi-node cases where each node has just a single GPU is known to fail. This will be addressed in a future release.
  • For the Llama 3.x and Llama 4 models, there is an issue with pipeline parallelism when using FP8 and NVFP4 weights. As a workaround, you can set the environment variable export TRTLLM_LLAMA_EAGER_FUSION_DISABLED=1.
