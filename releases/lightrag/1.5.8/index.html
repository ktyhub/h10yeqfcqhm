LightRAG v1.5.8

patch PublishedNov 23, 2026 SourceHKUDS/LightRAG

LightRAG v1.5.8

Important Notes

Highlights

1. Introduces a new storage type: Configuration storage

This store holds the key LightRAG configuration. It prepares the ground for gradually moving settings from the .env file into backend storage, and it also lays the foundation for the next step: account and permission management.

In v1.5.8 configuration storage holds each workspace’s embedding baselines: for every vector target (entities, relationships, chunks), the embedding space its vectors were written in. Changing the embedding model on an existing workspace now refuses startup.

  • Backends: JsonKVStorage, PGKVStorage, MongoKVStorage and OpenSearchKVStorage, selected with LIGHTRAG_CONFIG_STORAGE. Left unset, it follows LIGHTRAG_KV_STORAGE, so most deployments need no new setting. RedisKVStorage is not admitted, so Redis deployments default to JsonKVStorage, with a startup warning.
  • Several servers, one WORKING_DIR: supported on one host when each server has its own WORKSPACE and port, and all of them use the same configuration storage. A new anchor file, WORKING_DIR/config_storage_anchor.json, records the configuration backend and container. A server configured with a different backend or container is refused at startup. With JsonKVStorage as the configuration storage, each workspace’s configuration directory is claimed exclusively, so a second server on the same workspace is refused where the filesystem supports file locks. With a database configuration storage, two servers on the same workspace are not detected and remain unsupported.
  • Deployment anchor. The first start binds the deployment to its configuration container. It adopts the container’s identity UUID, or creates one, and records it with the backend type in WORKING_DIR/config_storage_anchor.json. Every later start checks both and refuses another backend type, another UUID, or a container that has lost its UUID (an empty or replaced database). Changing the host, port or credentials is not affected. A changed LIGHTRAG_CONFIG_STORAGE (or the LIGHTRAG_KV_STORAGE it follows when unset), a different database or a replaced database volume therefore no longer silently moves your configuration. Keep WORKING_DIR persistent and include the anchor in backups: a lost anchor rebinds on the next start with only a warning. To rebind on purpose, stop every server and delete the file.
  • New offline tools:
    • lightrag-migrate-config moves the configuration storage to a backend of another type, for example from JSON files to PostgreSQL.
    • lightrag-clear-storage clears a workspace offline, configuration storage and ancho file included.

For more information, see:

  • [lightrag/tools/README_REBUILD_VDB.md](https://github.com/HKUDS/LightRAG/blob/main/lightrag/tools/README_REBUILD_VDB.md), [README_MIGRATE_CONFIG.md](https://github.com/HKUDS/LightRAG/blob/main/lightrag/tools/README_MIGRATE_CONFIG.md), [README_CLEAR_STORAGE.md](https://github.com/HKUDS/LightRAG/blob/main/lightrag/tools/README_CLEAR_STORAGE.md)

2. PostgreSQL storage defaults

The setup wizard now generates PostgreSQL from the official pgvector/pgvector image and offers PGTableGraphStorage (plain tables, no Apache AGE) for the graph. PGGraphStorage (AGE) and the Redis storages (RedisKVStorage, RedisDocStatusStorage) are deprecated. They keep working and log a warning at startup.

3. Safer graph writes and document deletion

  • Manual graph edits (create / edit / delete / merge entities and relations, insert_custom_kg) are now serialized against each other and against the ingestion pipeline on NetworkXStorage.
  • Commit ordering for entity/relation create, edit, merge and rename was reworked to prevent data loss when an operation is interrupted.
  • Interrupted document deletions are visible and retryable.
  • The rebuild that follows a document deletion now re-extracts a surviving chunk whose extraction cache is missing, so the deleted document’s content no longer stays in the graph. A failed rebuild fails the deletion (retryable) instead of reporting success.
  • New lightrag-repair-chunk-tracking tool removes orphan chunk-tracking rows left behind by an interrupted deletion.
  • New lightrag-gc-llm-cache tool reports, and with --apply deletes, LLM extraction cache rows whose chunk no longer exists. See [README_GC_LLM_CACHE.md](https://github.com/HKUDS/LightRAG/blob/main/lightrag/tools/README_GC_LLM_CACHE.md).

4. Security hardening and new provider

  • The Ollama-compatible /api/* routes are protected by LIGHTRAG_API_KEY (see Breaking Changes).
  • The WebUI signs in with accounts only and no longer stores or sends an API key (see Breaking Changes).

Breaking Changes

  • Python 3.11 or later is required. Python 3.10 is no longer supported.
  • Changing LIGHTRAG_KV_STORAGE after the first v1.5.8 start is refused while LIGHTRAG_CONFIG_STORAGE is unset, because the configuration storage would silently move with it. Either set LIGHTRAG_CONFIG_STORAGE to the anchored backend explicitly, or move the configuration with lightrag-migrate-config.
  • Ollama routes require the API key. When LIGHTRAG_API_KEY is set and WHITELIST_PATHS is unset, /api/* requests without the key now get HTTP 403. In Open WebUI, the lightrag:latest model disappears from the list. Fix: enter the key as the API key of the Ollama connection (sent as Authorization: Bearer <key>), or set WHITELIST_PATHS=/health,/api/* to keep the old behaviour.
  • The WebUI no longer accepts an API key. /webui and /workspace do not prompt for, store or send an API key. A server protected by LIGHTRAG_API_KEY alone now shows a configuration guidance page instead of the application. Fix: keep the API key, set AUTH_ACCOUNTS and a strong TOKEN_SECRET, restart, reload the WebUI tabs and sign in. API keys keep working for programmatic API access. Deploy the WebUI and the server from the same version.
  • A chunk size below 64 tokens is refused. CHUNK_SIZE, CHUNK_F_SIZE / CHUNK_R_SIZE / CHUNK_V_SIZE / CHUNK_P_SIZE, addon_params, LIGHTRAG_PARSER rules and REST chunking.params used to accept any value. A smaller value now fails at startup, is rejected at enqueue, or gets HTTP 422. Documents already enqueued are not affected.
  • Library callers: a failed query raises. aquery() / query() / aquery_llm() / query_llm() used to return None or status == "failure" when the query failed. They now raise the exception, and the API server answers HTTP 500. A query that finds nothing still returns normally. An answer that contains only a <think>…</think> reasoning trace and no text is also raised as an error, and is not cached.
  • POST /documents/clear_cache is removed. Use DELETE /documents?clear_llm_cache=true instead. Clearing the LLM cache now happens together with the destructive clear.
  • Workspace names starting with $ are reserved. The server used to serve WORKSPACE=$team as _team. Set WORKSPACE=_team (the name your data is already stored under), and no data moves.

Upgrade Notes

  1. Back up first, then stop every old instance before starting v1.5.8. That includes all workers, servers sharing the storage, and maintenance tools. The first start creates the configuration container and binds the anchor. Do not do a rolling upgrade that leaves an old writer running.
  2. WORKING_DIR must persist, even if every storage is a database. It now holds config_storage_anchor.json, and for JSON configuration also <workspace>/kv_workspace_config.json. In Docker, keep it on a mounted volume. In Helm, keep persistence.enabled: true. An ephemeral WORKING_DIR loses the anchor and the JSON configuration on every restart. Include it in your backups.
  3. The embedding service must be reachable during the first start, so the adoption probe can record the baselines. Check the startup log for a WARNING that a baseline could not be established. If the start refuses with an embedding-space mismatch, your stored vectors do not match the configured model: fix the configuration, or run lightrag-rebuild-vdb.
  4. Redis users: with LIGHTRAG_KV_STORAGE=RedisKVStorage, the configuration storage defaults to JSON files in WORKING_DIR (see note 2). Redis storage is deprecated; plan a move to PostgreSQL.
  5. PGGraphStorage users: your deployment keeps working, and the wizard keeps the AGE-enabled image for it. To leave AGE, migrate the graph first ( refer to lightrag/tools/README_MIGRATE_GRAPH_STORAGE.md ).
  6. Optional: to keep the configuration in your database instead of JSON files, run lightrag-migrate-config --target-backend PGKVStorage (or MongoKVStorage / OpenSearchKVStorage) with every server stopped. Then set LIGHTRAG_CONFIG_STORAGE to that backend.
  7. To start over with a new embedding model, use lightrag-clear-storage rather than deleting files by hand. If you do delete files by hand, also remove kv_workspace_config.json and config_storage_anchor.json. Otherwise the recorded baseline refuses the new model.
  8. TOKEN_SECRET should be a random value of at least 32 bytes (for example, openssl rand -hex 32). The upgraded PyJWT warns about shorter secrets.
  9. Milvus users: the vector index always uses the COSINE metric. MILVUS_METRIC_TYPE is deprecated and ignored. A collection built with L2 or IP is re-indexed in place on the first start. No vector is re-embedded, but the collection is unavailable while the index rebuilds, so upgrade one instance first. Collection loading is now bounded by MILVUS_LOAD_TIMEOUT (default 600 seconds). Raise it if your largest collection needs longer to load, or startup fails. After a successful lightrag-rebuild-vdb or a workspace clear, the previous model’s Milvus collection is dropped. See [docs/MilvusConfigurationGuide.md](https://github.com/HKUDS/LightRAG/blob/main/docs/MilvusConfigurationGuide.md).
  10. Timeouts now reach the provider clients. LLM_TIMEOUT (default 240 seconds, also per role), EMBEDDING_TIMEOUT and RERANK_TIMEOUT are passed to every provider client, also for library callers. A call that used to run past the timeout on the SDK’s own default is now cut and retried. Raise the timeout for slow models. A value of 0 or below means no timeout.
  11. Query keyword extraction has a new KEYWORD_EXTRACTION_JSON_MODE (auto | json_object | none, default auto). auto requests JSON mode and retries once without it when the provider rejects the field. This fixes empty local / global / hybrid results on servers such as LM Studio.
  12. Account passwords longer than 72 bytes (UTF-8) are rejected by lightrag-hash-password, because bcrypt reads only the first 72 bytes.
  13. Optional: run lightrag-gc-llm-cache (report only; add --apply to delete) to remove extraction cache rows left behind by documents deleted on earlier versions.
